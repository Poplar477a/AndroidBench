# UFS Benchmark —— 问题与交付说明

> 状态：**已完成最终冻结版验证**。第 3 节全部结论均来自冻结版产物与两台 arm64 真机实测，
> 设备端 sha256 等式校验通过（一加 15 与红米均为 `530f3db7…`）。

## 1. 项目简介

UFS Benchmark 是一个面向 Android 设备的**存储性能基准测试应用**，同时内置一组
**CPU / 内存层次算力基准**（SPEC CPU 2026 移植版）。

- 存储侧：自带 Iometer 风格的 Dynamo 引擎（C++ 实现，通过 JNI 调用），并在
  fio 二进制可用时提供 FIO 引擎作为第二实现；两者都支持顺序/随机、可配块大小、
  队列深度、并发线程数与读写混合比例。
- 算力侧：移植 SPEC CPU 2026 的 821.gcc_s、766.femflow_r、854.graph500_s 三个基准，
  自行实现算法并对输出做正确性校验；结果为**相对自标定基线的比值**。
- 界面：Jetpack Compose + Material Design 3，支持 Android 12+ 的壁纸动态取色（Monet），
  低版本回退到固定浅色/深色两套方案。

### 2.8 CPU 定向调优档位（-mtune 变体）
原生引擎按 CPU 微架构提供多档 **`-mtune` 调度调优**变体，并在结果中如实披露**实际生效的档位**；
当设备不受支持（例如 x86_64 运行环境）时，应用**明确播报降级**，而不是静默回退。

**共 9 档（arm64-v8a）**，由三种编译器编出：

| 档位 | `-mtune` | 编译器 | 覆盖 |
|:--|:--|:--|:--|
| baseline | 不指定 | NDK r30 内置 Clang 21 | 全部设备（默认） |
| x1 / x2 / x3 / x4 | cortex-x1 / -x2 / -x3 / -x4 | NDK r30 内置 Clang 21 | 骁龙 888 ~ 8 Gen 3、天玑 9000/9200/9300 |
| x925 | cortex-x925 | NDK r30 内置 Clang 21 | 天玑 9400 |
| c1ultra（实验） | c1-ultra | 独立 LLVM 23.1.3 | ARM C1 系列（Lumex） |
| oryon2（实验） | oryon-2-v1 | Qualcomm Snapdragon LLVM 19.0.0 | 骁龙 8 Elite Gen 5（SM8850） |
| oryon1（实验） | oryon-1 | Qualcomm Snapdragon LLVM 19.0.0 | 骁龙 8 Elite（SM8750） |

**为什么用 `-mtune` 而不是 `-mcpu`（重要，实测结论）**：
`-mcpu=cortex-x2` 会把代码自动向量化成 **SVE** 指令，而 SoC 内的**小核（如 Cortex-A510/A710）
不实现 SVE**；Android 调度器会把线程调度到任意核心，代码落到小核即 **SIGILL 崩溃**。
实测对照：`-mcpu=cortex-x2` 编译的同源代码 SVE 指令 1 条；`-mtune=cortex-x2` 为 0 条。
故全部档位改用 `-mtune`（只影响指令调度，不启用目标核独有的 ISA 扩展）。

- **默认档位为公平基线**：定向调优是 opt-in，新安装一律 baseline，避免开启即崩溃
- 实验档**不进自动检测**，仅当本机确实可用时出现在设置页，且标注「实验性」
- 降级判定依据设备实际 ABI 与 MIDR，不支持时不谎报已启用调优
- 各变体的原生库需逐个通过 **16 KB 页对齐**校验（Android 15+ 要求）

1. 正常完成 → 结束即删除探测文件

**设备端等式校验**（两真机均通过，设备端 `sha256sum` 直接取值，不经传输）：

    一加 15 (<OnePlus15-serial>)  设备端 == 本地 == 530f3db7…   PASS
    红米   (<Redmi-serial>)           设备端 == 本地 == 530f3db7…   PASS

> **检查有效性自证**（避免"恒定通过"的假检查）：
> - 16 KB 对齐：NDK r30 的 libc++_shared.so → 16384（通过）；NDK r25c 同一文件 → 4096（判失败）

## 4. 已知限制与未验证项

### 4.1 已修复但需回归确认
- **次轮不刷新**：跑过一轮后再跑，界面显示上一轮结果。根因是运行中面板错误地读取了
  累积的历史记录（首轮为空故正常，次轮非空则误判为「已结束」）。
  已改为独立的「本轮结果」状态，运行中一律走实时面板。
  回归要求：**连跑两轮、期间不重启应用**。

### 4.2 优化等级（已在冻结版上实测）
工具链已升级为 **NDK r30 / Clang 21**，以下为冻结版实测值（从产物内编译参数串提取，非沿用旧结论）：

| 构建类型 | 全部 9 档实际生效 |
|:--|:--|
| Debug | **-O3** |
| Release | **-O2** |

Release 的 -O2 来自 AGP 对 RelWithDebInfo 追加的 `-O2`，覆盖了基础 `-O3`。

**因此不应使用 debug 与 release 两个包比较绝对性能**，也不应据此得出系统性差异结论。

**同一包内的 9 档已对齐优化等级**（Debug 全 -O3、Release 全 -O2），
所以包内跨档位对比不再混入「优化等级不同」这一变量；
但实验档（c1ultra / oryon1 / oryon2）另用**不同编译器**，
跨编译器比较仍不可解释，界面与结果页对此有明确提示。

（该值由构建期从真实生效参数中提取并写入编译期宏，界面与 logcat 如实披露。）

### 4.3 SPEC 比值口径
本项目无法获得 SPEC 官方参考时间，基线由本项目按同参数自标定。
因此所有比值为「相对自标定基线」，**既不是 SPECspeed 也不是 SPECrate 官方成绩**，
不可与 spec.org 公布分数比较。展示比值时必须同屏声明。

### 4.4 模拟器环境
在模拟器中，存储读写实际由宿主机页缓存与宿主 NVMe 承载，
测出的 GB/s 级成绩与任何手机闪存无关，**不可作为真机成绩**。
应用会在仪表盘给出该有效性提示。

### 4.5 其他限制
- 缓存参与开启时数值包含页缓存命中收益，反映「应用视角体验」而非闪存裸速
- 无缓存档若 O_DIRECT 不被支持，直接判失败，不静默回退
- Monet 动态取色需 Android 12（API 31）及以上；低版本回退固定配色
- SPEC 移植版路径不产出 CPU 占用（该路径为纯 CPU + 内存负载，
  已用 M-Ops/s 算力指标表达计算强度，刻意不给出以偏概全的数字）
- 普通应用身份下 Android 13+ 受 SELinux 限制读不到 sysfs，硬件详情需专业模式
- **多档位构建需限制并发**：本机 20 核 / 7.9 GB 内存，release 要编 9 档 × 4 TU = 36 个作业，
  ninja 默认按核数拉起会 OOM（实测 `IO failure on output stream: Cannot allocate memory`）。
  需 `./build.sh --max-workers=4`。这是环境约束，不影响产物内容。

## 5. 复现步骤

1. 构建：`./build.sh assembleDebug`（或 `assembleRelease`）
2. 安装：`adb install -r <apk>`
3. 启动应用，确认底部五个页签：首页 / 测试中 / 自定义测试 / 历史报告 / 设置
4. 进入「设置」，确认无「检测环境 / Root 方案 / 截图并分享」类条目，
   且页尾有署名
5. 进入「自定义测试」，选择「标准读写（先读后写）」+「按时间」+ 5s，
   点「应用配置并立即开始测试」
6. 观察「测试中」页：进度推进、指标实时刷新、结束后出现结果面板
7. **不重启应用**，再次执行第 5 步，确认第二轮同样实时刷新、且不残留第一轮结果
8. 切回「自定义测试」，选「按容量」+ 8 GB + 「单项纯写」，
   确认压测持续到累计 8 GB 才结束，而非被默认时长提前掐断
9. 打开「历史报告」，进入任一条详情页
10. 切换系统深色/浅色，确认界面配色随之变化

## 6. 期望行为

- 测试进行中，各项指标按选定采样档位**实时**更新，不得停留在上一轮结果
- 按容量终止时以累计容量为准，不受时长设置影响
- 测试数据文件在正常完成、手动终止、强杀后重启三种路径下都会被回收

- 历史报告可查看详情
- 界面配色跟随系统深浅色与（Android 12+）壁纸动态取色
