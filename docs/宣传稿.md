# UFS Benchmark 0.1.0-Alpha

**一个尽量让结论"可以被核对"的 Android 存储基准测试工具**

> **项目性质：测试（Alpha）阶段。** 这是一个仍在内部验证中的工程，不是成熟产品。
> 本稿关于能力的每一处描述都标注了源码位置（行号对应当前工作区）。本仓库的文档存在已知的滞后与漂移，
> 凡与源码冲突之处，请**以源码为准**——这也是本项目自己写在文档里的规矩（docs/README.md:5）。

## 一、先说清楚它是什么

UFS Benchmark 是一个跑在 Android 设备上的存储性能测试应用（常规版 applicationId = com.ufs.bench，实验室版 = com.ufs.bench.lab；app/build.gradle.kts:66-88），
压测核心是 JNI + C++17 的原生引擎（app/src/main/cpp/dynamo_engine.cpp），界面用 Jetpack Compose。

它的定位不是"再做一个跑分 App"，而是尽量回答三个在移动端容易被含糊过去的问题：

1. 这次的数字，是从哪条 I/O 通道、有没有经过页缓存测出来的？
2. 读回来的数据，是不是真的和写下去的一致？
3. 参数是怎么定义的、波动有多大，哪些结论其实不该下？

对这三个问题，我们选择的办法是让**结果自己交代**，而不是靠文案来担保。

## 二、源码里可以查到的几点做法

### 1. I/O 通道由引擎自己交代，该失败就失败

- 引擎区分三种通道并如实上报：O_DIRECT、O_SYNC 回退、缓冲 I/O（dynamo_engine.cpp:94-110、1137-1139）。
- 无缓存参与模式要求 O_DIRECT；如果最终没走成 O_DIRECT，本次运行**直接判失败**并写明"结果不可信"，而不是悄悄降级给一个好看的数（dynamo_engine.cpp:1152-1159）。
- 另有一条一致性兜底：披露文案与实际通道相悖时会被改写（例如声称 O_DIRECT、实际却回退到 O_SYNC 或缓冲 I/O，dynamo_engine.cpp:1141-1151）。
- 非 root 时用 posix_fadvise(POSIX_FADV_DONTNEED) 提示内核丢弃页缓存（dynamo_engine.cpp:381、647）；专业模式（root）才走 drop_caches（dynamo_engine.cpp:47-51、539）。

需要如实说明的是：**"含缓存"模式本来就走缓冲 I/O**，所以 README 里"所有读写句柄均开启 O_DIRECT"这句绝对表述与代码的条件判断并不一致，该处应按过期内容看待。

### 2. 读取路径逐块做数据完整性校验

写入时每个 4KB 块会被打上确定性校验头（魔数 0x55465342，即 "UFSB" + 64 位块偏移 + 反码 + 伪随机序列，dynamo_engine.cpp:298-310）；
读取时逐 4KB 验证（dynamo_engine.cpp:710-720），聚合结论写入结果字段 verified 与 verify_detail（dynamo_engine.cpp:1120-1129）。
已记录的一次真机读测试中，校验了 5,131,264 个 4KB 数据块、0 处错误（docs/verified-facts.md:941-949）。

边界同样写清楚：校验只发生在**有读取**的阶段；纯写运行不产生校验结论，上层合并时"没有做校验的阶段不参与判定"（BenchmarkViewModel.kt:1096-1098）。

### 3. 波动和延迟的口径写在代码里，而不是写在宣传里

- 延迟给出 min / avg / max 与 p95 / p99，专业模式下追加 p50 / p999；按样本秩取值、不做插值（dynamo_engine.cpp:1021-1049）。
- 抖动 = 剔除前 10% 预热样本后的变异系数；掉速事件 = 相邻采样吞吐跌幅 ≥30% 的次数；稳态吞吐 = 去预热后的均值（dynamo_engine.cpp:1074-1104）。
- 采样间隔可选 5 / 10 / 25 / 50 / 75 / 100 ms，其他取值就近归一（IometerAccessSpec.kt:282-293）。
- 保真边界也披露：单次运行的延迟样本上限 100,000 条，超出后不再记录（dynamo_engine.cpp:763-765），因此长时测试的 p999 只代表被记录下来的那部分样本。

### 4. 参数模型按 Iometer 存取规范建模，并承认自己的近似

模型包含块大小（4K/8K/16K/64K/128K/1M/2M）、读写比例（0–100 可调）、随机/顺序、队列深度、线程数、时长或容量终止、采样间隔（IometerAccessSpec.kt:209-235；界面取值见 SpecificationScreen.kt:125-129、313-334）。

两点必须如实说明：

- 本引擎使用**同步** pread/pwrite，"队列深度"是以并发线程数近似的（实际并发上限 64），代码注释写明了这一点（dynamo_engine.cpp:605-610）。它**不等于** fio 意义上的异步队列深度。
- 模型层不做跨字段校验，越界值主要在界面层做 clamp（SpecificationScreen.kt:46-49）。

### 5. 两个引擎：一个随包，一个是可选

- **Dynamo 原生引擎**：随包提供（IBenchmarkEngine.kt:8-15）。
- **FIO 引擎**：可选。仓库内没有 libfio.so，找不到可执行文件时它**不会出现在引擎列表里**（FioEngineImpl.kt:26-42、BenchmarkViewModel.kt:389-392）。它的调用与解析代码在仓库中（可用 tools/build_fio_arm64.sh 自行交叉编译），但**目前不应被当作已交付能力**；另外它固定 --direct=1、固定按时长运行，并不读取缓存模式与容量终止设置（FioEngineImpl.kt:87-104）。

### 6. 内置 CPU/内存微基准：用上游代码，并接受官方值校验

- CoreMark 使用上游**未改动**的源码编译（仅重命名入口），运行后核对官方三个 CRC 已知值 0xe714 / 0x1fd7 / 0x8e3a（bench/coremark/bench_coremark.c:231-233）；不足 10 秒的跑分判 PASS，但会明确标注"不构成标准成绩"（同文件:245-262）。
- STREAM 与 tinymembench 是"内核化重写"而非原样搬运，与上游的差异逐条写在文件头（bench/stream/bench_stream.c:1-20、bench/tinymembench/bench_tinymembench.c:1-20）。
- 所有比值都相对"**本机自标定基线**"，界面必须同屏展示"相对本机自标定基线，非上游官方分数"（PresetSuites.kt:13；基线常量见 bench/builtin_bench.cpp:124-132）；在模拟器/虚拟机环境中不给出比值（BenchmarkViewModel.kt:1173-1178）。

### 7. BYOB：给外部预编译二进制一个沙箱（实验室版，需要 root）

BYOB（Bring Your Own Binary）指把外部预编译的 arm64 可执行文件（例如 SPEC CPU2017 的交叉编译产物）打包导入，在受限条件下运行并与参考输出比对。

- **准入**：ELF 必须是 aarch64（e_machine == 0xB7），且 DT_NEEDED 限于 Android bionic 白名单（ElfValidator.kt:12-20）。
- **沙箱**（在 fork 出的子进程中逐步建立）：netns 断网 → 降 uid/gid → capset 清空能力 → rlimits → chdir → seccomp → execve（sandboxed_runner.cpp:463-540）；seccomp 是自写的 BPF 程序，系统调用白名单 + 默认 KILL_PROCESS（sandboxed_runner.cpp:313-342）；超时由父进程按墙钟到点 SIGKILL（sandboxed_runner.cpp:549-576）。
- **判分**：逐行比对，数值按 |a-b| <= abs_tol + rel_tol*|b| 判定，不匹配不重跑（OracleVerifier.kt:37-43、79-86）。文档同时写明：这是"与参考输出一致"的一致性判定，**不代表任何官方成绩**（docs/byob-打包规范.md:43-45）。
- **实测范围很有限**：截至记录，真机上跑通的是 519.lbm_r 与 505.mcf_r 两个组件；x86_64（含带 ARM 翻译的模拟器）上会诚实失败，不给虚假成绩。

### 8. 结果与产物

- 分享卡是自绘 Canvas 导出的 PNG（定宽 1080、按实际内容高度裁剪），不是界面截图（ResultCardRenderer.kt:29-40）；页脚写明"成绩受温度、后台负载与剩余空间影响，仅代表本次测量"（同文件:348）。
- 导出经 MediaStore 落到 Documents/UFSBench；目前**没有 CSV 导出**（app/src/main 内检索 csv 为 0 命中）。

### 9. 一次"自我审计"的记录留在代码里

代码中保留了两处删除自造指标的痕迹：I/O 循环里曾经内嵌的"假算力模拟"已被整体删除（dynamo_engine.cpp:768-770），旧版把 CPU / 内存 / IO 三项加权拼出来的自造 raw_score 也已删除（dynamo_engine.cpp:1016-1019）。
我们愿意把"删掉一个能吹的指标"也当作这个工具的一部分。

## 三、我们刻意不做的事

- 不把"应用能跑完"当成"验证通过"（docs/verified-facts.md:337-339）。
- 不给微架构定向档位贴"更快"的标签：实测 -mtune / -mcpu 在本项目负载上均为负收益，因此现在**只剩 baseline 一档**（app/src/main/cpp/profiles.cmake:20-31）。README 第六节仍列着 10 个档位的表格，属于过期内容。
- 不在模拟器上给跨设备比值，不在 x86_64 上假装 arm64 组件能跑。
- 不做单次读数就下的性能结论；Android 构建非字节可复现，不同包之间不宜比较绝对性能。

## 四、当前状态与已知边界（请按测试性质对待）

1. 版本 **0.1.0-Alpha**（versionCode = 2，app/build.gradle.kts:27-28），minSdk 26 / targetSdk 34；standard 与 lab 两个 flavor。
2. **没有单元测试与仪器测试**（app/src/test、app/src/androidTest 下没有测试文件），回归目前主要依赖真机脚本与人工证据记录。
3. 文档与源码存在已知漂移（档位数量、FIO 是否随包、部分 SPEC 章节等），"以源码为准"是本项目自己定的规矩（docs/README.md:5）。
4. 实测样本主要来自两台设备（Redmi Note 12 Turbo / SM7475、一加 15 / SM8850），样本量小，不足以支撑严格的跨机型结论。
5. 沙箱与外部二进制测试需要 root；应用进程自身无法建立沙箱，必须另起一个 root 进程（PrecompiledRunner.kt:39-43）。
6. 对存储目标的合规判断（tmpfs / 模拟器 → 无效，loop / FUSE → 警告，StorageDetector.kt:218-247）目前**只作为提示**，还没有接进运行门禁；其中 FUSE"低 15%~30%"字样也没有本地实测支撑，请不要把它当作本项目的测量结论。

## 五、适合谁，不适合谁

**可能适合**：关心"测的是哪条通道、数据有没有被校验、波动有多大"的存储方向开发者与验证人员；愿意用 root / 实验室版跑外部二进制的人；需要一份可以被逐项核对的测量过程的人。

**不适合**：想要开箱即用、跨机型产出官方可比分数的跑分需求；想拿本项目的数字与 spec.org 公布成绩做对比的需求。
